# Primary Key Generation

Primary key generation creates identifiers for records before they are saved to the database. The system uses Snowflake-style BIGINT IDs generated by the application rather than database-generated auto-increment IDs.

Snowflake-style BIGINT IDs have these characteristics:

- They are 64-bit IDs built from a timestamp, machine ID, and sequence.
- They are available immediately in memory with no flush required.
- They are globally unique across instances.
- They are roughly time-ordered, which helps with debugging and querying.
- They remove guessability of plain sequential IDs.
- They remain compact BIGINT values for indexing and joins.
- They require no migration.
- They require a generator implementation and clock synchronization safeguards.
- They are less human-friendly than sequential integers.

Database-enforced auto-increment primary keys cause these problems:

- They require flush or commit because the database generates the ID only once the transaction is flushed or committed.
- They complicate batching, caching, and testability and cause issues around multiple flushes per transaction.
- They create performance implications because IDs are only known after flush, causing code to perform additional flushes just to obtain generated IDs.
- They produce sequential IDs that are trivially guessable, posing a security and privacy concern when exposed via APIs.
- They tie identity generation to persistence, reducing flexibility for service decomposition, replication, or multi-tenant setups.
